\section{Introducción}
  Para establecer los conocimientos obtenidos durante el recorrido de la carrera, el estudiante debe someterse a una actividad practica que requiera la implementación de dichos conocimientos ya se mediante su inserción al mercado laboral, el desarrollo de una tesis o la incorporación a un proyecto tanto de investigación o de producción ya existente. Este documento trata con el ultimo caso, en el cual se le permitió al estudiante incorporarse al proyecto \emph{RT-Constellation}\footnote{Un reporte técnico completo presentando \emph{RT-Constellation} está disponible en: \url{https://github.com/clpombo/clpomboRxiv/blob/main/rt-constellation\%20white\%20paper.pdf}.} bajo la tutela del docente Carlos G. Lopez Pombo.

  La incorporación del estudiante se apoya en la existencia de un problema que este posee la capacidad de resolver. El eje central del trabajo es la reingeniería de la herramienta \emph{RT-Constellation}, ya desarrollada en conjunto con INVAP S.A.U.\footnote{\url{https://www.invap.com.ar}.}, y funcional, profundizando una de sus características centrales, la de estar pensada como una constelación de agentes que cooperan a través de una infraestructura de comunicación para poder verificar el comportamiento de un sistema de software. 
  
 Actualmente la herramienta funciona de la siguiente forma, se estructura como una arquitectura descentralizada (por eso se define como una constelación) diseñada para aislar la ejecución del Sistema Bajo Prueba (SUT) de las tareas de verificación. El objetivo de este diseño es evitar que el proceso de análisis, que requiere un alto nivel de procesamiento computacional, se convierta en algo que modifique el tiempo de ejecución del SUT. Para lograrlo, el procesos se divide en agentes independientes que se comunican según el tipo de rol que tengan (productor o consumidor) a travez de una infraestructura de paso de mensajes construida con RabbitMQ \footnote{Disponible en: \url{https://www.rabbitmq.com}.}. 

 El ciclo de ejecución de \emph{RT-Constellation} esta centrado sobre dos agentes:
 \begin{itemize}
  \item \emph{Event reporter} (\emph{RT-Reporter}):
    Este agente se encarga de dirigir la ejecución del SUT en un hilo independiente, adquiriendo los datos en tiempo de ejecución para producir un un flujo de eventos que es enviado a un \emph{RabbitMQ exchange} de comunicación llamado \emph{Event exchange}, y
  \item \emph{Runtime Monitor} (\emph{RT-Monitor}):
    Este agente actúa como consumidor conectado al \emph{Event exchange} y se encarga de implementar el análisis lógico leyendo y decodificando los eventos entrantes según su clasificación. Durante el procesamiento de eventos, el monitor verifica si la ejecución cumple con las restricciones estructurales esperadas y utiliza un modulo evaluador de propiedades para confirmar su validez. Aparte de esto, el agente gestiona un diccionario con gemelos digitales para simular lógicamente y hacer un seguimiento del estado de los componentes internos del SUT que no son visibles al proceso de verificación.
 \end{itemize}
 Luego de que los eventos sean evaluados existe un proceso de salida e interpretación de resultados que consiste en lo siguiente:
 \begin{enumerate}
  \item El \emph{RT-Monitor} produce un veredicto sobre cada propiedad analizada y emite estos resultados hacia un nuevo canal de RabbitMQ llamado \emph{Analysis results exchange}. En caso de detectar una falla, la herramienta también reporta la especificación que sirve como evidencia del error.
  \item Diferentes agentes se encargan de leer esta información resultante de forma paralela para resumirla y/o procesarla.
  \item El agente \emph{Results Logger} (\emph{RT-Results-logger}) lee los resultados del intercambio y genera un reporte detallado en un archivo CSV.
  \item El agente \emph{Statistics Analyzer} (\emph{RT-Analysis-stats}) recopila las estadísticas durante el análisis, cuantificando propiedades fallidas o exitosas, y reportando la traza de eventos particular que ha sido ejecutada.
  \item Por ultimo, la herramienta también provee mecanismos para poder ejecutar nuevamente un análisis de forma idéntica; para esto cuenta con el agente \emph{Event writer} (\emph{RT-Event-writer}), que permite registrar los eventos emitidos inicialmente en un archivo, y el agente \emph{Event reader} (\emph{RT-Event-reader}), que permite volver a inyectar estos eventos leídos desde el archivo hacia el \emph{Event exchange}.
 \end{enumerate}

  Esta forma de trabajar que tiene la herramienta funciona y permite su ejecución exitosa, pero tiene un problema cuando se debe terminar su ejecución. Actualmente los únicos medios de comunicación de los que disponen los agentes de \emph{RT-Constellation} son exchanges destinados a datos producidos / consumidos en el proceso de verificación; así, cuando la ejecución debe terminar, por ejemplo, al encontrar una violación de una propiedad de la especificación, el \emph{RT-Monitor} envía un mensajes de terminación, denominado \emph{poison pill}, a los agentes que tienen un rol de consumidor de mensajes de veredictos. El problema que se deriva de este comportamiento es, de alguna forma, consecuencia de esta forma de trabajo; el momento en que el \emph{RT-Monitor} demuestra la invalidez de una propiedad, sería deseable que esto comunicara la terminación del proceso al \emph{RT-Reporter} que se encuentra ejercitando la ejecución del SUT, pero esto no es posible debido a que el único mecanismo de comunicación entre el \emph{RT-Monitor} y el \emph{RT-Reporter} es el \emph{Event exchange} en el que los roles de productor y consumidor no permiten que el \emph{RT-Monitor} produzca mensajes y el \emph{RT-Reporter} los consuma.

  El objetivo central de este trabajo será la implementación de \emph{exchanges} que posibiliten el intercambio de mensajes de control que permita a los participantes postear mensajes con instrucciones de forma que todos los participantes puedan notificar sus intenciones, y que el resto pueda actuar en consecuencia de estos mensajes. Esta infraestructura puede pensarse como la separación entre canales de comunicación dedicados, y específicos, para control y datos.

 \subsubsection{Casos de uso entre los agentes}
  Los casos de uso que habria entre agentes vienen muy ligados al inicio y finalizacioinc controlada de cada uno de los agentes. Mas detalladamente:
  \begin{itemize}
    \item \textbf{Deteccion temprana de la ejecucion del SUT: }Cuando se detecta la invalidez de una propiedad, el agente \emph{RT-Monitor} debe enviar un mensaje de terminacion al resto de agentes que interactuan con el, haciendo que terminen su funcionamiento de forma ordenada.
    \item \textbf{Sincronizacion de arranque: } Para que la "constelacion" funcione correctamente, los agentes consumidores tienen que ejecutarse antes que los productores. Cuando los consumidores esten listos para recibir datos, estos enviarian un mensaje a los demas agentes avisandoles que pueden comenzar su ejecucion. 
    \item \textbf{Fnalizacion ordenada del analisis: } Cuando se termina de ejecutar una analisis, el agente \emph{Event Reader} envia un mensaje a los agentes \emph{Results Logger} y \emph{Analysis stats} para que puedan terminar el reporte de forma correcta e iniciar uno nuevo.
  \end{itemize}

  \subsubsection{Comunicaciones para dar respuesta}
    Las principales comunicaciones a las cuales los agentes pueden ser del siguiente tipo:
   \begin{itemize}
    \item \textbf{Mensajes por asercion fallida: }Estas comunicaciones son las que tienen mayor prioridad, ya que cuando una propiedad tiene como veredicto que fallo, el protocolo a seguir es que el resto de participantes detengan sus procesos. 
    \item \textbf{Notificacion de intenciones y estado de agentes: }Este tipo de comunicacion notifica al resto de participantes el estado en el que un agentes se encuentra, por ejemplo iniciando, esperando, procesando, etc. 
    \item \textbf{Notificacion de finalizacion: }Al terminar sus tareas de forma exitosa, los agentes pueden notificarlo entre si para estar listos a comenzar un nuevo monitoreo.
   \end{itemize}

 \subsubsection{Situaciones para dar respuesta}
  Muy relacionado a los situaciones anteriores, las respuestas que hay que dar pueden ser las siguientes:
  \begin{itemize}
    \item \textbf{Invalidez de una propiedad: }La principal respuesta que este sistema tiene que ofrecer es la terminacion de los agentes que siguen ejecutandose a pesar de que el monitor haya encontrado un veredicto fallido, permitiendo asi ahorrar recursos.
    \item \textbf{Arranque desincronizado: }Existe la posibilidad de que se empiecen a generar eventos antes de que el monitor este recibiendolos. Para esto la respuesta que se busca es un bloque preventivo hasta que el monitor notifique que esta listo para recibir eventos.
    \item \textbf{Fin de eventos: }Cuando se inyectan eventos y se alcanza el final del archivo, la respuesta que se busca es que se envie una instruccion de finalizacion a todos los agentes para que se pueda concluir el trrabajo de los agentes para esos eventos y se pueda generar correctamente el analisis. 
  \end{itemize}
